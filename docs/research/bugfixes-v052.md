## 确定修复

| 流程 | 原问题 | 修复及边界 |
| --- | --- | --- |
| 资源搜索上下文 | 结果保留后编辑关键词可能让旧候选带上新查询；选择时重复点击可能重复保存 / 导航 | 候选绑定提交时的分类、关键词、来源，查询变化即清除，提交 / 选择期间防重入，异步完成后再次核对上下文 |
| 部分结果选择后停止等待 | 全来源搜索已有快来源候选、慢来源仍等待时，选择触发慢保存；此时停止等待改变generation，保存结束提前return绕过旧清理，使选择状态永久锁住 | 将整个选择流程纳入try / finally，以独立selection token清理本次状态；旧选择不会清掉更新选择的锁，停止等待后已有结果仍可重新操作 |
| 作品库 / 来源初始化 | 已创建repository但原始list仍未返回，第二个初始化调用提前完成，保存后被旧list覆盖内存状态 | 优先等待共享initializing promise再允许保存，三个并发 / 保存场景校验读取完成前不写入 |
| Android下载句柄丢失 | 恢复时只等下一次轮询才能发现失效句柄；直接恢复可能失败 | mobile_http仅匹配原生确切缺失记录消息时重建，直接resume无需先poll；pause / cancel正确处理确实缺失，权限 / 损坏 / 近似消息不重新提交 |
| 原生JSON等待 | 没有caller signal时仅传native timeout，若IPC回调不结束，前端永久pending | 自有超时信号默认10秒、自定义夹紧并取整到500–35000毫秒，与caller取消合并；同值传native，成功 / 失败 / 取消清fallback资源 |
| JSON读取错误 | `.json()`读取阶段的网络 / 取消错误被改成invalid_response，掩盖原因 | 只有SyntaxError转换成无效JSON，其他Error、原生string和caller原因原样交还；不扩展修改provider全局文案 |

取消只结束前端等待，仍由已有native timeout约束其余工作；没有宣称超时会强行终止所有底层系统请求。
